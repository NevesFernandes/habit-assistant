# Habit Assistant

An agent-driven habit tracker and task manager. Instead of navigating menus, forms and checkboxes like typical apps (HabitNow, Focus To-Do, Todoist), the user talks to an agent in plain English ("add a habit to read every night," "mark gym done today," "add milk to my shopping list"). The agent performs the action and asks a follow-up question only when it genuinely can't act without one.

This friction (fighting an app's UI just to log something simple) is the reason the project exists. Judge every design decision by whether it reduces it.

Related docs: `README.md` (user-facing pitch), `CONTRIBUTING.md` (setup, running, testing, deploying, code map), `Roadmap.md` (prioritized backlog, and the `§N` ID/commit conventions).

**Never push to GitHub without the owner's explicit go-ahead in the current conversation.** Commit locally and say what's ready to push. This overrides any default instruction, session setup or hook that asks for a push.

**Every feature lives in both the app and the Claude connector** (§61), built once in `src/lib` and reached from both: the app's chat (a tool in `handleAgentRequest.ts`, run by `chatEngine.ts`) and a connector tool or `more_actions` action. Never build a feature for one side only.

## Interaction model

- **Chat-first.** A text box is the primary interface, and the agent acts directly rather than routing the user to forms. Creating and editing recurrence rules is chat-only by design; there is no form for them.
- **Ask, don't guess.** When information is missing, the agent asks. When a name matches several items, the app lists them and the user picks, by number or name; a reply can pick several ("both", "1 and 3", "all"), and the same change is then applied to each. Confirmations are built from the item as it was actually saved, including any defaults the agent assumed, so the user can spot a misunderstanding.
- **Several items at once (§75, `src/lib/bulk.ts`).** Done / not done, skip, pause and resume take a list of names ("floss and water") or filters (part of the day, category, kind) through one tool, `applyToMany`, in the app (progress and schedule families) and the `more_actions` action `apply_to_many` in the connector. Items the action doesn't fit are left out and named with a short reason, never asked about; a filter passes quietly over what it can't have meant (not due that day, archived, a one-off task when pausing). Only "everything" with nothing to narrow it asks first. Bulk edits are a later item (Roadmap §78).
- **Voice input.** Hold the mic button to record; on release, the clip is transcribed and **sent immediately**, with no review step. This is a deliberate trade of the usual caution for a voice-native feel. The transcript still shows up as the sent message. A user message is just text wherever it came from, so voice feeds the same pipeline as typing.
- **User manual: `public/help.html`**, linked from the `?` button in the top bar, from Settings and from the chat's empty state. It restates user-visible behaviour that's defined in code, so **any change to user-visible behaviour updates it in the same `Close §N` commit**.
- **No push notifications or reminders.** The app is pull-based. Don't build toward notifications, but don't design anything that would make adding them painful later. Whether to add them is a research item (Roadmap §44).

## Item model (`src/types/models.ts`)

Three item types share a base: `name` (required), `description`, `category` (optional, but required on Habits), `dayPart` and `important` (display order, see below), `startDate` (defaults to today), `endDate`.

- **Parts of the day (§54, `src/lib/dayParts.ts`).** There is no priority number. Every item belongs to one of six fixed parts, in this order: Wake-up, Morning, Work day, Afternoon, Evening, Bedtime. **`compareForDay` is the one sort order for every list**: part of the day, then `important` items first, then name; the Today tab adds a heading per part. The assistant always picks a part for a new item (required in the create tools, never asked), and the confirmation flags it as assumed when the user's message named no time of day. `important` is a yes/no flag ("top priority"), shown as a star. Both change through chat (`newDayPart`, `newImportant`) or the picker (`DayPartPicker.tsx`), which sits on the item's own page and behind the ⋮ button on each row of the Today tab, so a wrongly assumed part is two taps to fix. Items saved before §54 have no part and show under "Not placed yet" until placed; their old `priority` number is never written again and only read as "important" when above 1 (`isImportant`), so no migration was needed. It is display order only: `occursOn`, stats and streaks don't look at it. Finer ordering inside a part is a possible later item (Roadmap §60).

- **Habit.** Recurring, with a completion type:
  - **Yes/No**: a toggle.
  - **Numeric value**: a number against a required target and a free-text unit, logged through chat (`logHabitProgress`).
  - **Timer**: minutes against a required target. Logged through chat, or with the live timer tab (`TimerView.tsx`, `useTimerSession.ts`). Timer state is device-local (`timerStore.ts`), survives backgrounding, and reopens *paused* after a full close; it never fast-forwards elapsed time. The user saves the result to the habit explicitly.
  - **Checklist**: resets per occurrence, with progress stored as a per-date snapshot in the completion log.
- **Recurring Task.** Same shape as a Habit (category, part of day, dates, recurrence), but tracking is only done/not-done per occurrence: no completion types. Since §63 it has a yes/no habit's stats (`asTrackable` in `taskStats.ts`).
- **Single Task.** One-off, done/not-done. An undone task rolls forward to today rather than appearing on every future day. `doneOn` (§63) records the day it was marked done, set and cleared only by `withDone` in `dataStore.ts`; tasks done before §63 have none.
- **Checklists.** One shared component (`Checklist.tsx`) in two roles: a Habit's completion type, which resets each occurrence, and a freeform attachment on either Task type (e.g. a weekly "go shopping" task used as a running list). On a Recurring Task each occurrence has its own list, derived per date by `recurringTaskChecklistOn` (`recurringChecklist.ts`), in one of two modes: **carry over** (default: an item lives from its `addedOn` until the day it's ticked, `doneOn`, so unticked items move on to the next occurrence) or **same list** (a routine, with ticks per date in `checklistDoneByDate`). This state lives on the task, not in the completion log, where an entry still means only "done". A task has a checklist once it's created with one ("…with a checklist inside", possibly empty) or gets its first item. The day view shows it behind a progress badge (`3/7`, even `0/0`) that expands to the list, and ticking the last item offers, never forces, marking the task done. **Removing** (§56) is separate from ticking: an item comes off with the × in `Checklist.tsx` or through chat (`removeChecklistItems`, one tool for all three item types; the engine finds the owner), and on a Recurring Task or a Checklist habit it stays stored with a `removedOn` date, so it's gone from that day on while earlier days keep it. For a habit this matters because a past day nobody ticked has no snapshot and is drawn from the habit's own steps, so those are read per date (`habitChecklist.ts`), never straight from `habit.checklist`. **Any change to a habit's steps counts from today and leaves the past untouched**, including `updateHabit`'s `newChecklistItems` (the new steps get `addedOn`, the dropped ones `removedOn`); it reaches back only when the user explicitly names an earlier day (`newChecklistItemsFrom`, `removeChecklistItems`' `date`), and never forward. A Checklist habit keeps at least one step. `removeTaskChecklist` takes the whole checklist off a task, back to a plain one, and asks first when the list still has items. Both tools are also in the `delete` tool set, so "remove milk from shopping" never has only the item-deleting tools to choose from.
- **Archive** (Habits and Recurring Tasks) sets `endDate` to today, keeping history and stopping future occurrences. **Bringing it back** (§77, `unarchiveItem` in `dataStore.ts`) removes the end date and stores the days it sat archived as a finished pause (`archiveGap` in `recurrence.ts`), so they count as neither done nor missed and coming back never breaks the streak: the one pause written in the past, over days that weren't due anyway. Removing or moving out a passed end date through an edit does the same. Routes: "Bring back" on the item's page (`ArchiveRow.tsx`), the chat's resume tools (`resumeHabit`/`resumeRecurringTask` bring back an archived item, ending any pause too), and the connector's `schedule` `resume` op or the `more_actions` action `unarchive`. **Delete** erases the item and its history. Single Tasks have no archive.
- **Skip a day** (§68, `src/lib/skip.ts`; Habits and Recurring Tasks) excuses one day, **today or later only: the app looks forward, users never manage the past.** It's a one-day pause flagged `skip: true`, so `occursOn`, streaks and stats need nothing new; history reports it as "skipped", and the Today tab still shows the item greyed with an Undo. Refused for a past day, a day already done (undo first), a day not due, and "N times a week/month" habits (no set day). `currentPause`/`upcomingPause` ignore skips (labels, resume), `pauseItem` keeps a skip it doesn't cover, and resume keeps skips ahead. Chat: `skipDay` (`undo` takes it back); connector: `schedule`'s `skip` op and the `more_actions` action `unskip`.
- **Pause** (Habits and Recurring Tasks) is a list of `{from, resumeOn?}` periods; `resumeOn` is the first day back and is optional for an open-ended pause. Paused days are not scheduled days, so they count as neither done nor missed and don't break streaks. Finished pauses are kept forever; dropping one would turn its days back into misses. A pause can't start in the past.
- **No completion changes on future dates.** Habits and Recurring Tasks block it outright. For a Single Task, the agent confirms and then moves the task to today. Editing an item's other fields from a future day is still allowed.
- **Marking done through chat** (`setHabitDone`, `setRecurringTaskDone`) sets rather than toggles, for any past or current day the item is due. For a Numeric or Timer habit, "done" logs the full goal (a bigger logged amount is kept); for a Checklist habit it ticks every item. Replies spell out what was recorded ("with 8 glasses", "by marking all checklist items done"). A stated amount still goes through `logHabitProgress`.
- **Completion log.** Un-completing deletes the log entry instead of recording an event: the log mirrors what's ticked, not a history. This is settled; no event history is planned.
- **Notes on a day (§67, `src/lib/dayNotes.ts`).** One short note per item per day in `AppData.notes`, kept apart from the completion log so un-ticking keeps it and a missed or future day can have one. A new note replaces it, an empty one removes it, deleting the item deletes its notes; 500 characters at most. A one-off task's note goes on the day it's marked. In chat a note rides with `setHabitDone`/`setRecurringTaskDone`/`logHabitProgress` (`note`) in the same save, or goes alone through `setNote`. **"Notes" naming a day ("today's run", "yesterday", a date) are a day note; with no day they mean the description** (§55): `classifyIntent.ts`'s `DAY_PATTERN` and the edit prose follow that. Shown in italics on the Today tab, in history answers and in the connector's `get_day`/`get_history`.

## Settings by chat (§69, `src/lib/settingsByChat.ts`)

Two settings change by chat, in the app and from Claude: the **first day of the week** (synced) and **reading replies aloud** (per device). A message with neither shows them. **API keys, the chat provider and voice transcription never change by chat**: a key typed into a chat would go to the model provider and stay in the history, so the chat points to Settings instead. In the app, read-aloud changes **this device** (`readAloud` in `ChatEngineDeps`, saving its `ttsEnabledByDevice` entry like the Settings toggle). Claude has no device, so from the connector it changes **every device**: each entry, plus `ttsEnabledDefault` for devices with none yet; the app re-reads it at sign-in and when it comes back to the foreground (`importTtsEnabled`). App chat: the `settings` tool in its own "settings" family; connector: the `more_actions` action `settings`. It acts and confirms without asking, since both are one message to switch back.

## Categories

A default starter set with icons ships out of the box: Quit a bad habit, Study, Sports, Social, Finance, Health, Work, Nutrition, Home, Outdoor, Other. Users can add their own. **Category is required on Habits only** (the agent picks the best fit, falling back to Other, so it never has to ask); it's optional on Recurring and Single Tasks. This keeps agent-created items low-friction.

## Recurrence (`src/lib/recurrence.ts`)

Supported rules: daily, specific weekdays, every N days, N times per week/month (flexible, not pinned to days), nth weekday of month (first to fifth, or last), specific yearly dates (MM-DD), and on/off cycles.

**`occursOn(item, date)` is the single source of truth for "is this due?"** Views, stats, streaks and the heatmap all ask it. That's why pausing needed no special cases elsewhere, so route new scheduling rules through it too. Where a week *begins* is a synced setting (`AppData.weekStartsOn`, Sunday or Monday, absent = Sunday; `WeekStartContext` in the UI) passed explicitly to `startOfWeek`/`completionsInPeriod` and the stats; weekday numbers in rules stay 0=Sunday. Switching regroups past weeks, deliberately with no per-period history of the setting.

**"Today" is the device's local calendar date** (`todayISO()` in `recurrence.ts`, built on `src/lib/today.ts`; §62), never the UTC date the app used before, which flipped the day at the wrong hour away from UTC. The app sends it to `/api/agent` (`clientTodayISO`; older cached apps fall back to the server's UTC date) and stores the device's IANA time zone as `AppData.timeZone` at sign-in and whenever it comes back to the foreground (so a trip is followed), so the Claude connector, which runs in UTC, can work out the user's today. Dates logged before §62 within a few hours of midnight may sit on the neighbouring day; there's no time of day stored to fix them by.

## Stats (`src/lib/habitStats.ts`)

Streak, best streak, completion %, and this week/month/year/all-time counts, per habit (`HabitsView`) and per category (`CategoriesView`). The "stats" tab (`Dashboard.tsx`) adds an overall meter, KPI tiles, a per-category breakdown, and a hand-rolled SVG calendar heatmap (`CalendarHeatmap.tsx`). The same heatmap, via `HabitHeatmap.tsx`, also sits on each habit's own page in `HabitsView`. There's deliberately no charting library.

**Task stats (§63, `src/lib/taskStats.ts`).** A recurring task goes through the habit stats as a yes/no habit (`asTrackable`), so its page shows the same block (`ItemStats.tsx`, shared with the habit page) and it joins the stats tab's heatmap picker. One-off tasks are counted together (`computeSingleTaskStats`): done this week/month/year by `doneOn`, all time, open today, coming up, carried over and the average days carried. The stats tab keeps habits, recurring tasks and one-off tasks in separate sections (`statsByKind`), so tasks never dilute the habit numbers. The app's chat answers stats questions with `getStats` (the "history" family), worded in `statsReply.ts`; the connector's `get_stats` returns the same numbers, tasks in `recurringTasks`/`singleTasks` sections.

**Resetting stats (§64, `src/lib/statsReset.ts`) never erases history.** It sets `statsFrom` (today, so today counts) on each item in scope at that moment (one item, a category, everything, optionally one kind); every stat counts from `statsCountFrom(item)` (start date or reset), the log and heatmap keep the past. The best streak survives unless the user explicitly asks ("including the best streak", `bestStreakFrom`). `statsUndo` keeps the dates from before the last reset (a second reset the same day keeps the first one's), so "undo the reset" puts them back. A single one-off task is refused; their done counts reset together. Always asked first. "Counting since" shows on item pages and per stats-tab section. App chat: `resetStats` (history family, `undo`); connector: `reset_stats` (frozen without a best-streak input, so **from Claude the best streak always stays**) and the `more_actions` action `undo_reset_stats`.

## Architecture

- **Frontend:** a PWA (React + Vite + Tailwind). One codebase serves Android (installed to the home screen) and desktop browsers. Public address: **https://habitassistant.app** (a Custom Domain on the Worker; the `*.workers.dev` address is off via `workers_dev: false`). The signed-out screen (`SignIn.tsx`) doubles as the public homepage; `public/privacy.html` is the privacy policy Google's consent screen links to, and like `help.html` it must track what data goes where.
- **Storage: the user's own Google Drive.** One JSON file in a *visible* "Habit Assistant" folder, not the hidden appDataFolder, so users can inspect and back it up. This is a deliberate choice over a hosted database: real data ownership, at a cost of $0 by construction. Near-simultaneous edits from two devices are detected with Drive's modifiedTime; on a conflict the app re-reads the file and replays the mutation (`driveClient.ts`, `DriveConflictError`), with no merge logic.
- **Auth:** Google Identity Services with scope `drive.file`, used for both sign-in and Drive access. Access tokens last an hour and are never renewed silently: once one is about to expire (or a save gets a 401), a Reconnect banner appears, the Google popup opens only from its tap, and any save waiting on it is replayed afterwards (`persist` in `App.tsx`, GitHub issue #7).
- **Server: one small Cloudflare Worker** (`src/server/worker.ts`; static assets served via `wrangler.jsonc`'s `assets`). Its only jobs are `/api/agent` and `/api/transcribe`, so provider keys never reach the browser. Storage still goes straight from the browser to Drive. This is a narrow, deliberate exception to "no backend," not an always-on server.
- **Claude connector (§61):** a second Worker (`src/mcp/`, `wrangler.mcp.jsonc`) serves a remote MCP server at `mcp.habitassistant.app/mcp`, so Claude can use the same Drive file through a custom connector. It signs users in with Google through a second OAuth client in the same project (`drive.file`), keeps their refresh tokens encrypted in KV, and runs each tool through `src/lib`, so app and connector can't disagree on what's due. Stateless, one MCP server per request. Tools: `get_day`, `find_items`, `get_history` and `get_stats` (read), `set_done`, `log_progress`, `create_item`, `update_item`, `checklist`, `schedule`, `set_time_zone` and `more_actions` (write), `delete_items` and `reset_stats` (destructive, ask first). Notes (§67) ride on `set_done`'s and `log_progress`'s `note` input or go alone through the `more_actions` action `set_note`. Skipping a day (§68) is `schedule`'s `skip` op, undone with the `more_actions` action `unskip`. Bringing an archived item back (§77) is `schedule`'s `resume` op or the `more_actions` action `unarchive`. Settings by chat (§69) is the `more_actions` action `settings`. What did I miss (§73) is the `more_actions` action `missed`. Bulk done, skip, pause and resume (§75) is the `more_actions` action `apply_to_many`. Export (§72) is the `more_actions` action `export`. Create and update reply with the app's own confirmation text from `confirmations.ts`, fed the user's message so "Assumed:" works the same. **The tool list is frozen** (§61 Phase 4): claude.ai keeps the list it fetched at connect time and users can only refresh it by reconnecting, so new capabilities become actions of `more_actions` (`MORE_ACTIONS` in `src/mcp/manageTools.ts`), which Claude lists at run time; never a destructive one there, since it would share that tool's "always allow". Every tool works in the user's today from the stored `AppData.timeZone`, and every `dataStore` call from the Worker passes that date explicitly (the trailing `todayISO` argument), never the Worker's UTC one. Saves follow the app's §21 rule: re-read and replay on a modifiedTime conflict, up to three tries (`src/mcp/persist.ts`). Because the connector can change the file while the app sits in the background, the app checks the file's modifiedTime when it comes back to the foreground and re-reads it only if it changed (items only; BYOK settings still sync at sign-in). The tool descriptions name plain day questions ("what's on today?") so Claude reaches for `get_day` rather than a calendar. Even so, a bare "what's on today?" can still go to the calendar, so `help.html#claude` points users to a "Habits" claude.ai Project with copy-paste instructions, or to naming Habit Assistant in the question; it also covers adding the connector and per-tool permissions. `privacy.html#claude` covers what the connector stores: Google tokens encrypted in KV, the account ID and email beside them unencrypted (grant metadata), all expiring after 90 days unused (`GRANT_IDLE_TTL`), and logs of tool, status and timing only.
- **Chat turn logic is UI-free.** Everything after "send" lives in `ChatSession` (`src/lib/chatEngine.ts`): calling the agent, running the tool call it chose, follow-ups ("which one?", confirmations) and the reply text. `App.tsx` drives it with the real Drive persist; `npm run test:chat` drives the same code headless against real models. **New chat behavior belongs in the engine and comes with a targeted scenario.**
- **History over a period (§66, `src/lib/history.ts`):** `getHistory` lists, day by day, what was done, missed, paused, still open today or coming up, with per-item totals and the last day each was done; "N times a week/month" habits report per period instead of misses. The app's chat reaches it through `getHistory` (the "history" family) and words the reply in code (`historyReply.ts`), since its model never sees the data; the connector's `get_history` returns it as JSON for Claude to word. **Summaries (§65, `historySummary.ts`)**: every history carries per-day totals (`daily`), and `summarizeHistory` adds the done rate against the same number of days before, per-week totals and highlights (longest current streak, most missed, most improved by 10+ points, every-due-day-done items). The app puts it on top of an everything answer; `get_history`'s result carries it with a `fields` explainer, so Claude words or draws the app's numbers and never recomputes them.
- **What did I miss (§73, `src/lib/missed.ts`)** reads only the misses of a period from §66's history: per item the missed days (most missed first; "N times a week/month" habits only for a finished period short of its target), then one-off tasks still carried over (first due on or before the period's end), and at most two forward-looking nudges (missed 3+ times and on at least half its due days: change its days or pause it; carried 7+ days: new date or drop it). **Read-only, never "mark them done"**: the app looks forward. With no period named it uses this week up to yesterday, or last week on the week's first day, and the reply says so; a period reaching today stops at yesterday. App chat: `getMissed` (history family); connector: the `more_actions` action `missed`, with the same `suggestions` text.
- **Export (§72, `src/lib/exportCsv.ts`)** turns a period's history into a CSV, one row per item per day where something applies (history's days, `allDays` so none are dropped), never past today. App chat: `exportCsv` (history family); with no period named it asks, never assumes. The reply carries the file as a `download` on the message (`ChatDownload` in `agentHistory.ts`), shown as a Download button in `Chat.tsx` (with a byte-order mark for Excel) and stripped before every model call (`withoutDownloads`). Connector: the `more_actions` action `export`, the same CSV as text for Claude to save, capped at `EXPORT_MAX_ROWS` (3,000). An Export button with a period picker is Roadmap §79.
- **Name matching** (`src/lib/itemSelection.ts`): an exact name wins; otherwise the app tries word forms and ignores generic words, and offers every match closest-first.

### LLM provider strategy

The agent layer is provider-agnostic: one `ProviderAdapter` per provider in `src/server/providers/` (Anthropic, Groq, Gemini, Workers AI, and a zero-cost `mock`). The app uses a hybrid cost model:

- **Shared free trial by default**, funded by the operator's key. **Gemini is the primary** (`gemini-flash-lite-latest`; plain Flash allows only 20 free requests a day) in both dev and prod. `TRIAL_PROVIDER` is committed in `wrangler.jsonc`'s `vars` because a dashboard variable of the same name gets silently overwritten on every deploy; this caused real incidents twice. Change providers in `wrangler.jsonc`, never the dashboard.
- **Failover chain:** primary → optional `TRIAL_FALLBACK_*` → optional Workers AI last resort. It moves to the next tier on transient errors (429/5xx), with a per-provider retry and a request timeout, and also when a provider rejects the trial's own key (§48; no retry for that). All three tiers have been verified live. In production the chain is Gemini, then **Groq as the fallback** (`TRIAL_FALLBACK_PROVIDER` in `wrangler.jsonc`, with its key as the `TRIAL_FALLBACK_API_KEY` dashboard secret; without the secret the tier is skipped). Groq's free tier is one key for all trial users, so it carries roughly one or two messages a minute while Gemini is down: a thin safety net, not spare capacity. Workers AI is not enabled.
- **Every request has to fit Groq's free tier (§58/§59):** 8,000 tokens a minute per key, and any single request above that is refused (HTTP 413). Three things keep requests small:
  - `classifyIntent.ts` sends only the tool families a message needs: `create`, `edit` (the update tools), `progress` (mark done, log an amount), `schedule` (pause, resume, archive), `delete`, `checklist`, `history` (stats and periods) and `settings` (§69). A short reply to a question is classified by what it answers (`classifyTurn`, §51). **`npm run test:payloadSize` holds each family to a budget; when it fails, shorten a rule or split a family, don't raise the number.** `npm run measure:payload` prints the sizes.
  - Every narrowed request carries an escape tool, `needOtherTools`: when the families chosen don't cover what was asked, the model names the ones it needs and the server runs the request again with those. Never treat a narrowed tool list as all the app can do.
  - When a provider refuses a request as too large (an unclassified message is about 16,000 tokens), the server asks the model which families it needs in a small first call and then sends only those (`sendRouted` in `handleAgentRequest.ts`). Gemini never takes this path.
  - Known limit: on Groq's free tier two mid-sized calls in the same minute can exceed the allowance, so a wrongly classified request (escape, then rerun) may come back as a rate-limit error there.
- **Bring your own key (BYOK)** is first-class: in Settings, users can plug in an Anthropic, Groq or Gemini key. BYOK settings sync across devices as plain text in the Drive file (reconciled at sign-in). The user chose this knowingly: without a backend there's no honest way to encrypt them, so Drive is the security boundary. The way out for a key with billing is **"Keep this key on this device only"** (§47), a per-key box in Settings that starts ticked for a new Anthropic key only. Such a key stays in localStorage (`settingsStore.ts`): `exportState` always leaves it out of the Drive file, and `importState` at sign-in never overwrites or deletes it. The choices that depend on it (it being the active provider, voice input using a device-only Groq key) stay on that device too. Two limits are documented in `privacy.html#device-only` rather than solved: Drive keeps a removed key in the file's version history for about 30 days, and another device still holding the old synced key can write it back.
- **Shared-trial cap:** a client-trusted per-user message counter (`SHARED_KEY_MESSAGE_CAP` in `dataStore.ts`) nudges users toward BYOK. It's **50 messages** (§40). It's an honour-system nudge, not enforcement: the counter lives in the user's own Drive file, and `/api/agent` and `/api/transcribe` deliberately don't authenticate callers (the operator's choice, made knowing anyone could call them directly). When the trial's models are unavailable (429/5xx/timeout), the chat's error reply also points to BYOK. A rejected trial key (deleted or revoked) counts too: the server answers it as a 503 (`isKeyRejected` in `providerErrorMessage.ts`). A user whose *own* key is rejected is told so and sent to Settings.
- **Debug log:** a password-gated Settings section shows the last 50 model calls (provider/model, latency, retries, intent bucket, message, reply/error). It's device-local, never synced, hidden unless the device was switched on by opening the app at `#debug` (`#nodebug` turns it off), and the `VITE_DEBUG_LOG_PASSWORD` gate is a speed bump, not security. Nothing is recorded while it's off. **When the agent replies badly, check which provider answered first.**
- The shared trial is a bootstrap mechanism. If it's ever strained, move users to BYOK or a paid tier; don't over-build for scale.

### Voice input

- The browser records audio with `MediaRecorder` and sends it to `/api/transcribe`, which forwards it to **Groq Whisper**. Audio is never stored or logged. STT has its own key (`STT_TRIAL_API_KEY`) and its own BYOK toggle, independent of the chat provider.
- **Guards against Whisper hallucinating on silence** (1.2s of silence came back as "Thank you."):
  - **Client-side:** Silero VAD (`voiceActivityDetection.ts`, `NonRealTimeVAD`) skips both API calls when a recording contains no speech. It **fails open**: if the model can't load, the recording goes through. The ~13MB `onnxruntime-web` WASM runtime is self-hosted in `public/ort/` and precached by the service worker. It doesn't need COOP/COEP headers, which could break Google Sign-in.
  - **Server-side:** a blocklist of known hallucination phrases in `handleTranscribeRequest.ts` acts as a backstop.
- Agent replies can be read aloud (browser speech synthesis; toggle in Settings).
- **Future work, not built:** slide-to-lock recording (Roadmap §45) and fully on-device Whisper (§46), both to be trialled on a branch before deciding to adopt.
