# Roadmap

A living, prioritized backlog for Habit Assistant. This is not a spec — it's a queue of what to build next, ordered top-to-bottom by priority (top = highest).

**How this file is maintained:**
- Referenced by name in conversation ("let's do the next roadmap item," "tackle the categories one") instead of being re-described each session — read this file for the actual requirements before starting work.
- Once a feature is implemented, tested, and committed, remove its entry. The commit history is the permanent record; this file only tracks *unbuilt* work.
- Priorities can change on request — reorder by moving the entry to its new position in the list. No two entries share a *position*; position in the list is the priority rank.
- New items can be inserted anywhere in the order on request, including between two existing entries.
- Each entry also carries a **Now / Next / Later** tag — a visual/query layer on top of the ordering, not a replacement for it. A Later item never outranks a Next item, and a Next item never outranks a Now item: all Now entries stay above all Next entries, which stay above all Later entries. Ordering *within* a tier is still just top-to-bottom position, same as before.
- **Item numbers are permanent IDs, written as `§N` — never `#N`.** `#N` auto-links to GitHub issue/PR number N in commit messages, and this repo already had real collisions (roadmap items reused the same digit as unrelated GitHub issues after renumbering, polluting their timelines — fixed 2026-08-20). An ID is assigned once, when an item is first added, and is **never reused**, even after that item is completed and removed — so position (priority rank) and ID are independent: an item's position can change freely, but its `§N` never does. IDs `§1`–`§3` are already retired to historical, now-removed entries (see commits `ff9eaf1`/`2b5bdac` for §1, `d5254af` for §2, `bc8446c`/`c640cae` for §3) — don't reuse them even though they don't appear below.
- **Next available ID: §24**
- See also `CLAUDE.md`'s "Open questions / to refine later" section for undecided design questions — those are a different kind of thing from the concrete, actionable items below.

## Now

### §23 — Automatic multi-provider failover for the shared trial
Discovered 2026-09-03 testing the live deployment: Groq and Gemini each failed for entirely independent reasons on the same day (Groq: this app's tool-schema payload is 8,572 tokens — genuinely bigger than `openai/gpt-oss-20b`'s entire 8,000 free-tier TPM ceiling, confirmed via a direct, cold-cache test against Groq's real API — not intermittent, a hard permanent block for that model; Gemini: real server-side 503 "high demand," Google's capacity issue, unrelated to payload). Right now the shared trial is hard-wired to one provider at a time (`TRIAL_PROVIDER`), so either provider having a bad day takes down the whole trial experience for every user — unacceptable for retaining first-time users, who'll churn after a couple of failures. Fix: in `handleAgentRequest.ts`, on a transient provider failure (429/503/5xx), automatically retry with a second configured provider before giving up and surfacing anything to the user — extends the provider-agnostic adapter design that's already there, and costs nothing extra (needs 2+ trial keys funded simultaneously, e.g. Groq + Gemini, both already free). Natural pairing with §22's retry logic, but a different axis (cross-provider, not same-provider retry).

Folded into scope: which Groq model actually belongs in the chain. `openai/gpt-oss-20b` (current default) can't fit this payload at all per the test above; `llama-3.3-70b-versatile` has a **12,000 TPM** ceiling, comfortably above the 8,572-token payload with no trimming needed — but its answer quality/latency for this app's tool-calling task is unverified. Alternative/complementary lever: trim the tool-schema payload itself (separate, smaller effort, doesn't require picking a different model) — see Claude's saved notes ("§23 multi-provider failover — Groq TPM finding") for the full test output and reasoning. Cloudflare Workers AI was also researched as a possible third fallback (zero extra account/key management, already same platform) but tool-calling quality on its free-tier models is unverified — not included in this item's scope, worth a separate look later.

### §20 — Nudge new users from shared key to BYOK after a few messages
Today the shared trial key (`TRIAL_API_KEY`, called from `src/server/worker.ts`) is available indefinitely to any signed-in user with no cap — fine for solo testing, but stops being sustainable once other people (e.g. a couple of friends) start using the app too. This is the exact trigger `CLAUDE.md`'s cost-model section already anticipated for revisiting BYOK-as-default. Needs: (1) a per-user message counter for shared-key usage, stored as a field in the user's own Drive data file and incremented client-side after each shared-key call, capped at **5 total messages**; (2) once the cap is hit, the chat responds with a guide message instead of forwarding to the LLM, and stops offering the shared-key path; (3) a small static onboarding webpage (hosted alongside the existing Cloudflare Pages site) walking a non-technical user through creating a Groq account, generating their own API key, and pasting it into Settings. Enforcement is intentionally client-trusted, not server-verified — see Claude's saved notes ("§20 shared-key nudge decision") for the rejected hard-gate and server/KV-enforced alternatives and why they weren't chosen at this scale.

### §21 — Replace Drive write-conflict handling: retry-with-replay instead of discard-and-ask
`writeDataFile`/`persist` (`src/lib/driveClient.ts`, `src/App.tsx`) already detect a conflicting write via a `modifiedTime` compare-and-swap, but today a conflict just discards the user's just-made edit, reloads the latest remote data, and tells the user to redo the action by hand — "last write wins," with the loser responsible for noticing and manually retrying. Not acceptable now that real cross-device (phone + laptop) use is starting. Fix: since every `dataStore.ts` mutation is already a pure `(data, input) => newData` function, on conflict `persist` should reload the latest remote data and **replay the same mutation function against it**, then retry the write (cap ~2 attempts, mirroring the existing 5xx-retry pattern already in `driveClient.ts`). This resolves the common case (edits to different items from two devices) invisibly and correctly, since replaying intent naturally merges around unrelated remote changes — it does not handle the rare case of the exact same field of the exact same item being changed on both devices within the retry window, accepted as low-stakes given usage is one person on their own devices. Bundle in while touching this code: (1) once retries are exhausted, surface a clear, specific error rather than a generic message — loud failures over silent ones; (2) `fetchWithRetry` should also retry once on an actual network/offline failure (today only retries on 5xx), and if it still fails, show a distinct "you're offline, this didn't save" message. Rejected a generic 3-way tree merge and a real CRDT/Automerge backing — see Claude's saved notes ("§21 Drive conflict resolution decision") for why.

### §22 — Retry-then-loud-fail for LLM ("agent") calls, matching §21's pattern
`fetchJson.ts` (shared by `agentClient.ts`/`transcribeClient.ts`) already distinguishes an offline failure, a server-unreachable failure, and a malformed-response failure with distinct messages, and `App.tsx`'s `handleSend` catch already surfaces whichever message loudly as a chat message — so the "loud fail" half of §21's pattern already exists for the LLM path, nothing to do there. What's missing is the retry half: neither the client's call to `/api/agent` nor the Worker's own call out to the underlying provider (Groq/Anthropic/Gemini, in `handleAgentRequest.ts`) retries a transient failure before giving up — a single network blip or provider 5xx surfaces immediately as an error instead of quietly succeeding on a second attempt. Fix, mirroring `driveClient.ts`'s `fetchWithRetry`: (1) client-side, retry once on a network failure or a 5xx-ish response from `/api/agent`; (2) server-side, retry once on a transient failure from the upstream provider call. Scoped to the chat/LLM path only, per explicit decision — voice transcription (routed through the same `src/server/worker.ts` to `handleTranscribeRequest.ts`) is a separate call path and intentionally not included here. **Also fold in (found 2026-09-03 debugging a live Gemini outage): no request timeout exists anywhere in this path** — neither the client's fetch to `/api/agent` nor the Worker's fetch to the provider (`groq.ts`/`gemini.ts`/etc.) has one, so a provider call that hangs instead of erroring leaves the chat stuck on "Thinking…" forever with no feedback at all. Needs a timeout (client and/or server side) that turns a hang into the same loud, clear failure a real error would produce — not just the retry-on-error logic above.

## Later

### §17 — Chart-based stats dashboard
Streak, best streak, completion %, and this-week/month/year/all-time counts are already computed (`src/lib/habitStats.ts`) and shown inline in `HabitsView`/`CategoriesView` — this item is the visualization/UX layer on top, not the underlying computation (already done). Needs: a dedicated dashboard page/view, and actual chart/graph visuals. **Library decision made (2026-09-02): skip a charting library — hand-roll stat tiles/KPI row/meter in plain HTML+Tailwind plus a small SVG calendar-heatmap component, rather than adding a dependency like Recharts/Chart.js/visx.** Full research and fallback options saved in Claude's memory (ask Claude to recall the "§17 chart library decision" notes) rather than duplicated here.

### §18 — Preserve full completion history on habit un-complete
`toggleHabitCompletion` (`src/lib/dataStore.ts`) deletes the `CompletionLogEntry` when a habit is un-marked, rather than recording the toggle as its own event — so the log reflects current per-occurrence completion state, not a true history of every completion/uncompletion. Low urgency today, but worth a deliberate decision (e.g. append a new entry type instead of deleting, or keep a separate audit trail) before any future stats work leans on "every completion event" being real, since that can't be backfilled after the fact.

### §19 — Live start/stop timer UI for Timer habits
Timer-habit progress is currently logged after the fact via chat (`logHabitProgress`) — a duration in minutes, the same simple mechanism as Numeric-value habits. The user has looked at HabitNow's Timer habits and wants that fuller experience eventually: an actual running stopwatch (start/pause/stop, elapsed time tracked live), not just after-the-fact entry. Deliberately deferred — real added scope beyond this pass (running-timer state, handling the app being backgrounded/closed mid-timer, persisting an in-progress session). The user will write a fuller spec before this is picked up.
